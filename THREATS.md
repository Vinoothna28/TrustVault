# TrustVault Threat Model & Security Defense Matrix (THREATS.md)

This document details the threat landscape, attack vectors, defensive architectures, automated verification, and accepted residual risks for **TrustVault**.

---

## 1. System Philosophy: Zero Trust & Separation of Powers

In TrustVault, security is treated as the foundational architecture, not an afterthought:
1. **Deny Access by Default**: No user or role has implicit permission to view or retrieve a document.
2. **Server-Decided Access**: The server computes authorization on every HTTP request and byte stream. No client-side checks or cached tokens bypass this.
3. **Immediate Revocation**: Document permissions are checked directly against the source of truth (MongoDB) on every download or read request. Long-lived signed URLs (like pre-signed S3 links) are avoided because they cannot be immediately invalidated upon revocation.
4. **Separation of Duties (Least Privilege)**: System Administrators oversee system health, user lifecycle, and audit integrity, but **cannot view confidential documents** unless the document owner explicitly grants them permission.
5. **Tamper-Evident Auditability**: Every access attempt—successful or denied—is logged into an append-only, SHA-256 cryptographically chained audit log.

## 3. Honest Disclosure of Known Limitations & Accepted Trade-offs

1. **In-Band Database Hash Chaining vs. External Hardware / Cloud HSM**:
   - *Current Implementation*: We implement a cryptographic SHA-256 hash chain inside MongoDB where each record stores the hash of the previous record.
   - *Honest Assessment*: If an adversary gains full write access to the MongoDB server, they could alter a historical record and recompute all downstream hashes from that point forward.
   - *Why Accepted*: In a self-contained system without third-party cloud infrastructure (e.g. AWS QLDB or an RFC 3161 Time-Stamp Authority), in-band hash chaining successfully prevents casual or isolated modifications and guarantees sequence continuity. In an enterprise production deployment, the latest hash would be anchored periodically (e.g. hourly) to an immutable external ledger or public blockchain.

2. **File Streaming Performance vs. Immediate Revocation**:
   - *Current Implementation*: All document downloads stream through the Node.js Express server to ensure per-request permission checks.
   - *Honest Assessment*: For massive enterprise deployments with millions of concurrent gigabyte-sized files, streaming through application instances consumes socket descriptors and CPU compared to offloading to S3 pre-signed URLs.
   - *Why Accepted*: Pre-signed URLs have a mandatory expiration window (e.g. 15 minutes) during which access **cannot be revoked**. If an employee is terminated or access is revoked, a pre-signed link remains functional until expiration. Immediate revocation was an absolute requirement of this challenge, justifying the streaming architecture.

3. **Soft Deletions vs. Cryptographic Shredding**:
   - *Current Implementation*: When an owner deletes a document, it is marked `isDeleted: true` to preserve the audit trail reference and prevent dangling foreign keys in audit records.
   - *Honest Assessment*: The physical bytes remain on disk in `backend/storage/documents/`.
   - *Why Accepted*: In legal compliance (e.g. SEC Rule 17a-4 / FINRA), records must be preserved for regulatory hold periods. A future enhancement would implement cryptographic shredding where each document has a unique AES-256 key: deleting the key makes the on-disk file unrecoverable while leaving the audit log intact.
